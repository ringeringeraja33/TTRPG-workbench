# Repeatable local acceptance

Run the complete verification batch with one command:

```powershell
python -X utf8 scripts/verify_workbench.py --output C:/private-reports/workbench-run-01
```

The output must be a new directory outside the repository. Existing directories are rejected. Each run executes all discovered unit/integration tests, capability freshness checks and six replay scripts: actions, combat, exploration, investigation, both campaign fixtures and Keeper cases. It then detects campaign/local-Dice databases generated by those replays, validates and backs up each, checks file hashes and compares recovered state. It never scans or alters real campaign files elsewhere on the machine.

`report.json` records stage status, elapsed time and archive results. Separate UTF-8 stdout/stderr files retain diagnostic details. The fixtures and private database copies are GM material; keep the output directory private. The process exits 0 only if every stage and archive check passed, 1 for an executed failure, and 2 for invalid setup. A timeout or subprocess launch failure marks that stage failed; independent checks continue. An empty set of database artifacts cannot yield a passing report. Each subprocess is bounded to 180 seconds.

The runner does not fix failures, edit code, regenerate stale coverage, commit, push or schedule future work. During development, inspect the failed stage's diagnostic files, make a bounded repair, then run a fresh verification directory. Do not overwrite previous evidence. Repository whitespace review (`git diff --check`) remains a separate development check because distributed skill copies may not be Git repositories.

The scripts use their existing mixture of original synthetic fixtures and real OS dice where declared. Passing results verify implemented behaviors; they do not establish exhaustive rules correctness, live-player quality or authenticity of arbitrary campaign histories.
