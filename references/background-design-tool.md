# Background pack check contract

Run `python -X utf8 scripts/background_design.py <pack.json> --chargen <spec.json>`; add `--player` for public output. Both paths are explicitly supplied; the pack cannot select arbitrary files to read. The numerical adapter is CoC7 only. Other systems use the prose workflow and their own creation validation.

Required pack fields: `profile` (must equal creation profile exactly), `premise`, `sources`, `skills`, `items`, `scenes`, `start`, `gm_secret`. The `history` source ID is required for these historical packs. Sources map IDs to objects with `status` (`read`), `locator`, and `scope`. Missing or unread evidence produces draft status. A previous read may be used with explicit access limitations recorded in scope. No network or source authentication occurs in the checker.

Skills: `{id, name, treatment, base, cap, source, use, limit}`. IDs and bases must match the supplied creation profile; occupation/interest budgets remain authoritative there. Each skill must occur in a route. Additional skills require editing and revalidating the creation profile, not merely adding a decorative name here.

Items: `{id, name, source, availability, acquisition, quantity, price_basis, procedure, effect, limits, upkeep, substitute}`. Quantity is a positive integer. Availability is `scenario allocation` or `source verified`; the first is a fictional allowance, the second requires external review of actual source text. This is a description of access, not a date-based automatic verifier. New items are optional scene equipment, not silently inserted into the original starting cards. The checker verifies links and fields, not inventory spending or native-system action legality.

Scenes: `{id, title, purpose, entry, exit_condition, npc, objects, clue, pressure, exit, routes}`. A route has `{id, method, skills, items, success, failure, cost, outcome}`. `skills` and `items` are required capabilities/equipment IDs, not OR alternatives. `success` and `failure` are scene IDs or `END`; `outcome` describes the actual consequence. An empty requirement list describes an ordinary route, which still needs the stated fictional access and cost. Each scene must have at least one no-special-skill/no-item route. Every scene must be reachable; every declared branch destination must be known; every scene must reach END under ordinary routes on both success and failure. `exit: true` marks a scene with an END route. This strict condition is for these fail-forward investigation fixtures, not a universal adventure-design law.

Use the two independent projections: `audit(pack,spec)` returns errors/pending/card audit; `player_view(pack,result)` emits only status, premise, selected skill fields and selected item fields after valid checks. Invalid packs emit status alone; drafts retain their draft status. It omits scene IDs, clue facts, GM secret, source notes and internal extra fields. No string-level filter can detect a secret deliberately put in a public name or effect: inspect the resulting prose.

`walk(pack, failure=True)` returns an ordinary-route traversal from start, always choosing a reachable unvisited successor; cycles without an onward path fail audit. It is a structural traversal, not a simulated live game or proof that NPC cooperation makes sense. Tests and manual case walkthroughs together establish the declared fixture scope.
